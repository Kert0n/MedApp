# MedAppServer

Домашняя аптечка: что есть в наличии и что пора принять. Аптечки бывают общими — семья, соседи. Система приватна по замыслу: о человеке не хранится ничего, кроме идентификатора и хеша ключа.

Документ состоит из трёх частей: **что система должна уметь**, **как она устроена**, **что делаем**.

# Часть 1. Фичи и критерии

Перечень полный: и то, что уже работает и должно продолжать работать, и то, чего ещё нет. Отмечено: ✅ работает, ⬜ ещё нет.

## 1.2 Приватность

| | фича | критерий |
|---|---|---|
| ✅ | Минимум данных о человеке | В `users` только `id` и `hashed_key`. Ни имени, ни почты, ни телефона. |

## 1.4 Упаковки

**Ключевое понятие новой концепции: `Drug` — это упаковка, а не «лекарство вообще».**

| | фича | критерий |
|---|---|---|
| ✅ | Завести упаковку в аптечке | Аптечка задаётся путём: упаковка не существует сама по себе. |
| ✅ | Прочитать, править описание | Отсутствующее поле в PATCH означает «не трогать». |
| ✅ | Исправление количества | Только исправление учёта — в любую сторону. **Пополнения не бывает: докупил пачку — завёл вторую упаковку.** |
| ✅ | Списание | Съеденное уменьшает упаковку. **Списать больше, чем в упаковке, нельзя** — это физика, а не политика. Различия «приём по плану» и «расход вне плана» больше нет. |
| ✅ | Ноль уничтожает упаковку | Пустая пачка выбрасывается: списание до нуля удаляет запись вместе с бронями на неё. |
| ✅ | Перенос между аптечками | Брони тех, кто целевую аптечку не видит, не переживают переезда. |
| ✅ | Точные количества | `NUMERIC(19,6)`, округление вниз; половина таблетки не превращается в `0.49999999999999994`. |
| ✅ | Упаковка не знает о бронях | Ни суммы внутри агрегата, ни «доступного остатка», ни пропорционального пересчёта. |

## 1.5 Брони

**Второе ключевое понятие: бронь — заявка человека на часть упаковки, со своей жизнью.**

| | фича | критерий |
|---|---|---|
| ✅ | Завести, прочитать, изменить, отменить | Одна бронь на пару «человек и упаковка». Отмена — это удаление; брони с нулём не бывает. |
| ✅ | Бронь может превышать остаток | 30 таблеток в пачке, забронировано 40 — нормальное состояние. **Сервер не чинит планы клиента**: сколько из брони оставить, решает её владелец. |
| ✅ | Бронь не переживает упаковку | Бронь на выброшенную пачку бессмысленна и исчезает вместе с ней. |
| ✅ | Мои брони по всем упаковкам | Один запрос, не зависящий от числа упаковок. |
| ✅ | Своя версия у картины броней | Токен принадлежит снимку броней на упаковку, а не отдельной брони: изменить свою долю, не увидев общей суммы, нельзя — иначе решение принимается вслепую. Слито в #100. |

# Часть 2. Архитектура

## 2.1 Ограниченные контексты

**Аптечка** — основной. Упаковки, брони, аптечки, участники, пользователи.

**Справочник** — данные внешнего скраппера Vidal. Только чтение, наполняется мимо приложения, своя причина меняться. Отдельный контекст.

**Shared kernel** этих двух — `QuantityUnit` и `FormType`. Единица измерения обязана быть одной на систему; копия по контексту означала бы, что «шт» из каталога и «шт» из упаковки — разные вещи.

**Журнал приёмов** — отдельный контекст за портом. Причина не техническая: приёмы слишком персональны, чтобы лежать в нашей БД. Сегодня реализация в памяти процесса, завтра очередь или внешний сервис. Критерий, по которому проверяется, что граница проведена верно: **смена хранилища меняет репозиторий, а не сущность.**

## 2.2 Модель

### Упаковка — `Drug`, aggregate root

Физически это пачка. Её нельзя пополнить: две пачки — две упаковки. Пустая пачка выбрасывается.

Состояние: `id`, `medKitId`, `name`, `quantity: Quantity`, `formType?`, `category?`, `manufacturer?`, `country?`, `description?`, `version`.

Инварианты: количество строго положительно (нулевой упаковки не существует — она уничтожается); единица величины неизменна, кроме явной перевески.

Команды: `describe(details)`, `changeQuantityTo(q)` — исправление учёта, `consume(amount): Drug?` — `null` означает «пачка кончилась и подлежит уничтожению», `relabelUnitTo(unit)`, `moveTo(targetMedKitId)`.

**Чего в агрегате нет и не будет:** броней, их суммы, доступного остатка, пропорционального пересчёта. Упаковка не знает, кто на неё претендует.

### Бронь — `Reservation`, aggregate root

Заявка человека на часть упаковки. Идентичность — пара `(userId, drugId)`.

Состояние: `userId`, `drugId`, `amount: Quantity`. **Версии у брони нет** — токен предусловия принадлежит картине броней на упаковку (`ReservationSnapshot`): менять свою долю, не видя общей суммы, значит решать вслепую.

Инвариант ровно один: количество строго положительно. Отмена брони — это её удаление, а не бронь с нулём.

**Чего у брони нет:** ограничения сверху. Бронь может превышать остаток, и это не ошибка, а нормальное состояние, за которое отвечает владелец.

Связь с упаковкой — по идентификатору, не по ссылке. Бронь не переживает уничтожения упаковки: это правило целостности данных (внешний ключ с каскадом), а не отношение владения — JPA-каскада и `orphanRemoval` между ними нет.

### Аптечка — `MedKit`, aggregate root

Состояние: `id`, `members: Set<UUID>`, `version`. Инвариант: участник хотя бы один. Членство — дочерние строки `user_med_kits` внутри агрегата.

### Пользователь — `User`, aggregate root

`id` и `hashedKey`. Правило одно: пользователя без ключа не существует. Реализует `UserDetails` — принятое отклонение: домен зависит от `spring-security-core`, потому что пользователь и есть тот, кем его представляет аутентификация.

### Приём — `Intake`, entity

`id` (придуман клиентом), `userId`, `drugId`, `amount`. Идемпотентность — не приём кеширования, а следствие идентичности: приём с таким идентификатором либо записан, либо нет.

### Значения

`Quantity` — число и единица вместе; нормализация масштаба и вся арифметика внутри типа, величины в разных единицах не складываются. `QuantityUnit`, `FormType`, `DrugTemplate`.

## 2.3 Слои: где какая логика

| слой | что здесь живёт | чего здесь быть не должно |
|---|---|---|
| `domain` | **Бизнес-правила.** Инварианты в конструкторах; команды возвращают новое состояние, а не меняют текущее. Знание «упаковка не пополняется», «бронь может превышать остаток», «нулевой упаковки не бывает» — здесь и только здесь. | Аннотации персистентности, HTTP, знание о хранилищах. Из Spring — только `UserDetails`, отклонение названо выше. |
| `db/model` (`*Data`) | **Работа с ORM.** Отображение на строки и ничего больше. `var` — требование Hibernate, а не разрешение менять поля откуда угодно. | Любые решения. Ни одного метода с правилом. |
| `db/repository` | **Работа с БД.** JPQL, нативные запросы, массовый DML, индексы. Это адаптер Spring Data, а **не** Repository из DDD. | Доменные типы, транзакции, проверки доступа. |
| — | **`EntityManager` в рабочем коде запрещён совсем.** `flush`, `clear`, `detach`, `refresh`, `getReference` — оснастка тестов: ими подгоняют persistence context под ожидания. В проде они означают запись, выстроенную вокруг того, когда именно Hibernate что-то сделает. Держит `NoEntityManagerTest`. | |
| `db/store` (`*Store`) | **Repository в смысле DDD** — граница агрегата. Принимает и отдаёт только доменные типы; внутри — отображение, сборка агрегата, заявка на изменение корня. | Бизнес-правила, коды HTTP. |
| `services/aggregate` | **Один сервис на агрегат.** Прочитать состояние, вызвать метод домена, отдать хранилищу. Проверка доступа и правила, относящиеся к этому агрегату. Единственный, кто видит `db/store` своего агрегата. | Правила чужих агрегатов, SQL (за хранилищем), DTO, Spring MVC, **открытие транзакции**. |
| `services/orchestrator` | **Сложная комбинация агрегатов.** Домен на входе, домен на выходе. Появляется, когда сценарий нужен больше чем одному фасаду или несёт правило взаимодействия, а не последовательность. | **Что угодно про клиента:** DTO, коды ответа, клиентские идентификаторы. Открытие транзакции. |
| `services/application` | **Один сервис на ресурс** — то, что клиент и заказывает. Владеет транзакцией, переводит в DTO, зовёт несколько сервисов подряд и передаёт результат одного другому. Только это видит контроллер. | Сложная комбинация — она ниже. Хранилища. |
| `api` | DTO публичного контракта и сборка их из доменных типов. | Правила, обращения к БД. |
| `controller` | Перевод HTTP: разбор предусловий, коды, теги, валидация формы запроса. | Правила, репозитории, сущности. |

**Словарь, который надо держать в голове при чтении:** `db/repository` и `db/store` — разные вещи с обманчиво похожими именами. Первое — ORM-адаптер, второе — DDD-репозиторий. Переименование в свой PR; здесь фиксируется значение.

**Прикладной слой режется по сценарию, а не по числу задетых агрегатов.** Это ошибка, которую пришлось исправлять: деление «один агрегат / больше одного» — свойство реализации, и клиент про него ничего не знает. Оно протекло наружу — контроллер обязан был выбирать между сервисом и оркестратором по признаку, невидимому из HTTP, а класс, названный по агрегатам, которых касается, собрал в себе всё, что трогает два из трёх.

Правила, по которым слой держится:

1. **Контроллер видит один сервис на ресурс.** Сервис зовёт другие сервисы, но не хранилища: до агрегата ходят его сервисом.
2. **Фасад тонкий.** Ему позволено позвать несколько сервисов подряд и передать результат одного другому — и всё. Сложная комбинация уезжает в оркестратор или в сам агрегат.
3. **Фасады не зовут друг друга.** Понадобилось двоим — значит, общее лежит слишком высоко и должно уехать вниз, а не расти вбок.
4. **Оркестратор про клиента не знает.** Домен на входе и на выходе. Всё клиентское стекается в прикладной слой — и **поэтому** за его толщиной следят особо: дай знанию протечь ниже, и кандидат в боги просто сменит имя.
5. **«Можно ли делать операцию» решает тот, кто за неё отвечает.** Агрегат знает, кто он и как себя проверить; вызывающий спрашивает и отдаёт операцию дальше.
6. **Транзакцией владеет фасад.** Ниже — `propagation = MANDATORY`: границу требуют, но не открывают. Иначе владельца use case из кода не видно, и всё держится на `REQUIRED` по умолчанию.

Все шесть закреплены рефлексивным тестом.

Названное исключение одно: `AuthenticatedUserService` зовёт фильтр безопасности, и границы вокруг ещё нет — он открывает свою. Это точка входа наравне с фасадом, просто вход не из контроллера.

## 2.4 Доступ

> **Каждое чтение, отдающее данные наружу, принимает вызывающего.** Либо предикат членства стоит в самом запросе, либо принадлежность выражена ключом строки. Третьего варианта нет.

| агрегат | чем держится доступ |
|---|---|
| `Reservation` | **ключом**: составной внешний ключ ведёт на членство, поэтому брони без доступа не существует. Отдельного снятия броней при выходе больше нет — это тот же каскад |
| `Drug` | **предикатом**: `EXISTS` по `user_med_kits` через `med_kit_id` пачки |
| `MedKit` | **предикатом**: `EXISTS` по `user_med_kits` |

Отдельного шага «проверить доступ» нет: чтение и есть проверка. Поэтому и слова «accessible» в именах нет — различать нечего, другого чтения не бывает. Признак — сам параметр `userId` в сигнатуре, и его наличие проверяет `QueryScopeTest`.

Пессимистичных блокировок в чтениях нет: `@Lock(PESSIMISTIC_WRITE)` снят вместе с `lockAccessible`.

**Категории «родитель уже проверен» нет.** Она держалась на дисциплине вызывающего, а дисциплинарные правила забываются первыми.

**Объект — доказательство доступа, идентификатор — то, что надо проверить.** Отсюда разделение: **чтение принимает идентификатор** и несёт предикат, **команда принимает агрегат**. Если команде нужен идентификатор, она берёт его у объекта сама; принять его снаружи значит согласиться, что вызывающий проверку прошёл, — а проверил его никто. Читает фасад, один раз, и передаёт вниз уже доказанное. Держит правило `CommandsTakeAggregatesTest`.

**Перегрузка вместо чтения в фасаде.** Основная форма команды берёт агрегат; рядом стоит перегрузка по идентификатору, которая честно читает и зовёт основную. **Своё читает сервис агрегата, чужое — оркестратор:** сервису знать про соседний агрегат не положено. Фасад остаётся тонким — компоновка запроса и ответа, — и читает сам только там, где собирает ответ из нескольких агрегатов.

**Исключений нет, включая вступление по приглашению.** Оно перестало быть чтением чужой аптечки: `join` вставляет строку членства и читает аптечку уже как участник. Отсутствие аптечки и повторное вступление приезжают нарушениями именованных ограничений.

Разобранные альтернативы и почему не они:

- **Postgres RLS.** Обойти нельзя ничем, но правило уезжает в базу вопреки нашему же запрету прятать там логику, а личность вызывающего надо надёжно прокидывать в сессию через пул. Отклонено; к вопросу не возвращаться без новой причины.
- **Фильтры ORM (`@Filter`).** Не применяются к загрузке по идентификатору — то есть ровно к тому пути, на котором дыра и была.
- **`@PostAuthorize` / `@PostFilter`.** «Загрузить и выбросить»: грузит недоступное в память и ломает пагинацию.
- **ReBAC-сервис (Zanzibar, SpiceDB, OpenFGA).** Несоразмерно трём агрегатам и требует держать отдельную систему согласованной с собственной базой.

## 2.5 Конкурентность и целостность

Три разных вопроса, которые легко свалить в один механизм — и один раз уже свалили.

| вопрос | чем отвечаем |
|---|---|
| «есть ли у человека право на это?» | **запросом**: читаем то, что видно вызывающему, и не находим чужого |
| «согласованы ли связанные строки?» | **ключами**: правило живёт в коде, ключ страхует |
| «не затёр ли я чужую запись?» | **версией** той сущности, которую записываю |

**Версия отвечает только за свою сущность.** Она не артефакт доступа: нужно проверить, что человек всё ещё в аптечке, — идём и проверяем, а не удерживаем чужой токен. Прошлый заход держал версию упаковки и состав аптечки «как основание решения», и это разъезжалось: версия аптечки двигалась от вступления постороннего, а отказ получал тот, кого это не касалось.

| механизм | что делает | где |
|---|---|---|
| предикат версии в `UPDATE` | ловит потерянное обновление: ноль задетых строк — гонку проиграли | упаковка, снимок броней, аптечка |
| отдельный `UPDATE` по строке корня | двигает версию, когда меняется агрегат, а не его строка | только аптечка: состав лежит в другой таблице |

**Команда предъявляет версию того, к чему обращается.** Упаковка — версию упаковки, бронь — версию брони, аптечка — версию аптечки (выход, удаление, удаление с переносом). Создание упаковки, приглашение и вступление предусловия не требуют: они ничего не перезаписывают.

Версия двигается тем же оператором, что и состояние: `version = предъявленная + 1` идёт частью `UPDATE`, а предикат `version = предъявленная` стоит в его условии — от прочитанного объекта здесь не берётся ничего, иначе версия могла бы уйти вниз. Присваивать её отдельно нечему — Hibernate, который ею распоряжался, ушёл в #96.

**Замерено:** заявка на изменение корня применяется перед коммитом, а не при `flush`, и складывается с обычным приращением от dirty checking. И: массовый DML с `clearAutomatically` очищает persistence context, унося вместе с ним зарегистрированную `OPTIMISTIC`-проверку — проверено вычитанием, снял из сценария один этот запрос, и та же гонка стала отвергаться. Второй замер — причина, по которой удержание чужого агрегата не выжило бы даже технически.

Несовпавшее предусловие — 412: оно предъявлено и не выполнено. Проигранная гонка отвечает так же — предъявленное было верным на чтении и устарело к записи, но база различает эти случаи одинаково, нулём задетых строк, да и клиенту разницы нет. 409 остаётся конфликтам, предусловием запроса не бывшим: дублю брони и версиям из тела синхронизации. Авто-повтора нет ни там, ни там: сервер не знает, останется ли команда осмысленной по новому состоянию.

### Правила в коде, ключи — сеть безопасности

Бронь живёт с упаковкой и человеком, а не с членством, и переезжает вместе с пачкой. Правило одно:

> **Назначение переживает переезд, если человек допущен к целевому хранилищу, и снимается, если не допущен.**

Коробку переставили на другую полку; для того, кто к полке допущен, ничего не изменилось. Правило описано в `DrugRelocation` и в домене (`Reservation.survivesRelocationTo`) — читающий DDD-слой обязан увидеть его целиком, не заглядывая в схему.

Схема то же самое **страхует**: `med_kit_id` на броне и составные внешние ключи `(drug_id, med_kit_id) → user_drugs(id, med_kit_id)` с `ON UPDATE CASCADE` и `(med_kit_id, user_id) → user_med_kits` с `ON DELETE CASCADE`. Гонка между переездом и выходом не оставит брони без доступа даже там, где код не успел.

**Триггеров в базе нет.** Hibernate не видит изменений, сделанных мимо него: строка, обновлённая триггером, разъезжается с версией в памяти, и ни `@Generated`, ни `@Formula`, ни колбэк JPA этого не закрывают — замерено. Логика — в бизнес-правилах, база держит ключи.

## 2.6 Синхронизация

Клиент копит события офлайн и присылает суммы, а не поток. Но две кумулятивные величины — сколько съедено и какой стала бронь — это два разных ресурса, и порядок между двумя запросами не гарантирован. Разрыв реален: приходит списание, срабатывают уведомления «лекарства мало», и только потом уменьшение брони.

Поэтому единый запрос, атомарный **на упаковку**:

```
PUT /v1/drugs/{drugId}/sync/{syncId}
{
  "consumed": "5.0",          // дельта; необязательно
  "drugVersion": 3,           // предусловие упаковки
  "reservation": {            // необязательно
    "amount": "20.0",         // абсолютное значение
    "version": 7              // предусловие брони; отсутствует, если брони ещё нет
  }
}
```

Версии переезжают из заголовка в тело **только здесь**: запрос меняет два ресурса, а заголовок один. В остальных местах предусловие остаётся заголовком. Отсюда и код ответа: несовпадение версии из тела — 409, а не 412.

Журнал повторов пишется **после коммита**. Кеш не участвует в транзакции, и запись по ходу команды пережила бы откат — повтор получил бы подтверждение того, чего в базе нет, а клиент вычистил бы офлайн-очередь.

## 2.7 Маршруты после изменений

| маршрут | что делает |
|---|---|
| `POST /v1/drugs/{drugId}/intakes` | единичный приём: списывает из упаковки. Заменяет `consumptions` — различия «по плану» и «вне плана» больше нет |
| `PUT /v1/drugs/{drugId}/sync/{syncId}` | пакетно и атомарно: приём вместе с новой бронью |
| `GET /v1/reservations`, `GET/PATCH/DELETE /v1/reservations/{drugId}` | брони вызывающего; переезд с `/v1/treatment-plans` |
| `PUT /v1/intakes/{intakeId}` | уходит в 404: маршрут отвечал `501` и ни разу не работал |

### Формы ответов

`DrugDTO` теряет `availableQuantity` — такого понятия больше нет. Имена словарей (`quantityUnit`, `formType`, `category`) в нём тоже не нужны: единственное, что даёт справочная запись, — название, и его отдаёт словарь.

Вместо голого `DrugDTO` маршруты упаковки отдают **снимок**:

```
DrugSnapshotDTO { drug, reservations { total, mine } }
```

Пачка не знает про брони, но клиенту нужны обе величины сразу — сумма заявленного и своя доля. Собирается это в `api`, чтением броней одним запросом на весь набор.

Аптечка отдаёт **состав**, а не содержимое: список идентификаторов упаковок, а не вложенные объекты. Снимок пользователя — `{ id, medKits, drugs }`: плоско, без дублирования одной пачки в двух местах.

## PR 5 — схема из одного источника ✅ слит (#99)

**Дыра, которую открыл #96, и её надо закрыть раньше, чем схему начнут править версии.**

`SchemaValidatesTest` держал согласие `db/schema.sql` с моделью суждением самого Hibernate: база создавалась файлом, приложение поднималось с `validate`. Hibernate ушёл, тест удалён — и теперь прод поднимается по `db/schema.sql`, а тесты по `Tables.kt`, и разойтись они могут молча. Ровно те два источника истины, против которых тест и стоял.

Вместе с ним ушли ещё два, и оба зря:

- `CascadeSchemaTest` проверял каскады в самой базе — правило части 1 «без переноса содержимое уходит каскадом». К ORM отношения не имел, удалён заодно.
- `SchemaContractTest` проверял свойства самого файла: создание с нуля без `ALTER`, точный тип количеств, каскады у детей и их отсутствие у пользователя, `CHECK` на положительность. Устарел в нём ровно один пункт из пяти — про `ddl-auto=validate`.

**Решение — один источник.** `Tables.kt` описывает схему, `db/schema.sql` из него порождается, и тест сверяет порождённое с закоммиченным, как `OpenApiSnapshotTest` сверяет контракт. Тогда прод и тесты поднимают одно и то же по построению, а не по договорённости.

Возвращаются `CascadeSchemaTest` целиком и `SchemaContractTest` без пункта про `validate`.

## PR 6 — версии, предусловия и синхронизация ✅ слит (#100)

`version` в схеме и домене; заявка на изменение корня у аптечки; массовый DML двигает версию сам. Коды 428/400/412/404. Команды возвращают записанную версию.

**По ревью переделано главное.** Предъявленная версия стала обязательным параметром записи: `save(drug, stated)` не собирается без неё, и предикат `UPDATE` берёт предъявленное, а не версию прочитанного. `Preconditions` с забываемым `requireStated` исчезли; в теле версию разворачивает превращение запроса в команду, ниже границы контракта обнуляемых версий нет. Отсюда и код: проигранная гонка отвечает **412**, как и всякое несовпадение, — различать «прислал устаревшую» и «проиграл гонку» база не даёт. 409 остался дублю брони и версиям из тела синхронизации.

**Переезд сделал этот PR проще, и риск из него ушёл.** `@Version` у Exposed нет, и не нужен: предикат версии пишется в самом `UPDATE`, а проигранная гонка видна по числу задетых строк. Замеренная несовместимость `@Version` с триггерами перестала существовать вместе с `@Version` — сравнивать и увеличивать версию теперь нечему, кроме нашего же запроса.

Тесты гонок: списание, членство, перенос против выхода, одновременное создание. Проигравшая сторона обязана получить отказ, а состояние — совпасть с результатом победившей.

**Сюда же перевод нарушений именованных ключей в доменные отказы.** Правила «одна бронь на пару» и «дважды не вступают» выражены в коде и проверяются чтением; ключи их страхуют, но на настоящей гонке отдают нарушение ограничения. Переводить его в отказ имеет смысл там, где гонки заводятся под тест. Оговорка про другие имена ограничений на H2 снимается: H2 из сборки ушёл, тесты идут на Postgres.

## Регламент

1. Каждый PR — прямо в `main`, с зелёными тестами и полным описанием. PR не сливаю сам.
2. **Сначала открываю PR с описанием, потом работаю.** Читать нечего, пока PR нет: ветка → первый шаг → PR (черновиком, если не закончено) с полным замыслом → остальная работа, дополняя описание по ходу.
3. Индексирую **только файлы своего PR** явными путями (`src/MedAppServer/src`, `src/MedAppServer/db`, `src/MedAppServer/open-api.yaml`): рядом лежат untracked-файлы пользователя, `git add -A` запрещён.
4. **Модель и запросы идут раньше кода, который на них стоит.** Сервисы, написанные под чтения, которые вот-вот изменятся, приходится переписывать — ровно тот случай, которого требует избегать пункт про недоделанные фичи. Проверено на #93: прикладной слой слит с ручной проверкой доступа вместо механизма, и следующий PR её снимает.
5. Каждый PR и каждый коммит делает одну вещь. Замеченный по дороге беспорядок записывается сюда, а не чинится на месте.
6. Ни один эндпойнт не публикуется в полуработающем виде.
7. Число запросов и производные величины проверяются **по SQL-логу, а не рассуждением**.
8. Механизмы фреймворка проверяются замером, а не документацией по памяти; результат замера идёт в описание PR.
9. `open-api.yaml` регенерируется механически по ходу; осмысленный проход — один раз, в PR 10.
10. На каждый PR — **свой подплан** отдельным файлом с подробным разбором. Этот документ обновляется при планировании, а не дописками задним числом.
